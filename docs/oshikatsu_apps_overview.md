# 推し活YouTubeツール — 概要仕様書

作成日: 2026-08-30
対象: 既存4アプリ（新着一覧 / 未視聴チェック / TOP9タイル画像 / ワードクラウド）の統合と是正
詳細仕様: 別紙（図解版）

---

## 1. 目的

### 解決する課題

| # | 課題 | 本質 |
|---|---|---|
| 1 | シクフォニはグループ＋個人で7チャンネルあり、供給が多くて追い切れない | **消費の可視化** — 何が出た？ 何をまだ見ていない？ |
| 2 | YouTube中心の推し活は、グッズやファンアートに比べて「こう推している」を伝える手段が少ない | **推し活のアウトプット化** — 視聴とコメントを見せられる形にする |

### 今回のゴール

4機能はすでに別々のアプリとして動いている。ゼロから作るのではなく、**共通のボトルネックを直して繋ぐ**のが本件のスコープ。

1. 4アプリが**共通の動画マスタ**を見るようにし、YouTube API のクォータ枯渇を解消する
2. ソースに直書きされた **API キーを止める**
3. TOP9画像アプリを**実データ（英語ロケールの Takeout）で動く**ようにする
4. ワードクラウドを「概要欄」から**「自分のコメント」入力**に作り替え、Colab から Streamlit へ移して他の人も使えるようにする

---

## 2. スコープ

| | 機能 | 解く課題 | 入力 | 出力 |
|---|---|---|---|---|
| **A** | 新着一覧（昨日 / 今週 / 今月） | 1 | なし | 期間別の動画リスト |
| **B** | 未視聴候補 / リピート推奨 | 1 | `watch-history.json` | 絞り込み可能な動画リスト |
| **C** | 視聴回数TOP9タイル画像 | 2 | `watch-history.json` | 3×3 の PNG |
| **D** | 自分のコメントのワードクラウド | 2 | `comments*.csv` | チャンネル別7枚＋全体1枚の PNG |

A・B が「見る」ため、C・D が「見せる」ためのツール。

**対象外**: 日次再生数の収集・ランキング分析（既存の `sixfonia_analytics` パッケージと Colab ノートブックが担当）。TSV を手で用意する `ranking_top10_image` 系の導線は本件では使わない。

## 4. 目標構成

4アプリを1つのリポジトリ（`unofficial_sixfonia_youtube_tools`）に集約する。

```
unofficial_sixfonia_youtube_tools/
├── sixfonia_analytics/            共通パッケージ（config / snapshot / takeout）
├── .github/workflows/
│     update_snapshot.yml          毎日 JST 23:00
│       → apps/web-arrivals/public/data/videos.json をコミット
├── apps/
│   ├── web-arrivals/   A: 新着一覧（昨日/今週/今月）   Vercel・入力不要
│   ├── web-viewer/     B: 未視聴チェック               Vercel・watch-history.json
│   └── streamlit/      C: TOP9タイル画像 ＋ D: ワードクラウド
└── tests/
```

**スナップショットを同じリポジトリに置くのが要点。** Actions 既定の `GITHUB_TOKEN` は
自リポジトリなら書き込めるので PAT が要らず、コミットが入れば Vercel が自動で再デプロイする。
Streamlit からは新着一覧アプリが配信する公開URL（`/data/videos.json`）を読む。

A・B はどちらもブラウザから YouTube API を呼ばない構成へ寄せる（B は移行中）。

## 5. 主要な決定事項

| # | 論点 | 決定 |
|---|---|---|
| 1 | 動画マスタの取得 | 都度取得をやめ、**毎日夜1回のスナップショット**にする。`search.list`（100 units）を `playlistItems.list`（1 unit）へ置き換え、**700 units/表示 → 約200 units/日** にする |
| 2 | スナップショットの配置 | 同一リポジトリの `apps/web-arrivals/public/data/videos.json`。PAT が不要になり、公開URLになるので Streamlit 側からも同じものを読める |
| 3 | Vercel の構成 | 1リポジトリから**2プロジェクト**。Root Directory を `apps/web-arrivals` / `apps/web-viewer` に向けるだけで済む。A を B に統合するより手数が少なく、B の大きな `page.tsx` に触らずに済む |
| 4 | API キー | ソースから除去し、`.env.local`（gitignore 済み）と Vercel 環境変数に置く。**キーのローテートは未実施**。恒久対応はサーバー側 route handler へ寄せること |
| 5 | チャンネルの判定方法 | 視聴履歴の `subtitles` ではなく **`videoId` × 動画マスタの突合**。削除・非公開動画や YouTube Music 経由の再生も正しく拾えるため |
| 6 | 「未視聴」の定義 | **7チャンネルの全動画**を対象にし、履歴に無いものを未視聴候補とする。履歴の保存期間による不完全さは注記で明示する |
| 7 | 新着一覧の期間区分 | **昨日 / 今週 / 今月の3区分**。「今日」は作らない — 今日の動画は YouTube ですぐ見られるし、夜のバッチではその日の分をまだ取得できていないため |
| 8 | Shorts と長尺 | セクションは**分けない**。ただし未視聴一覧は本数が多くなるため、絞り込みトグルだけは持つ |
| 9 | TOP9画像 | 期間フィルタあり。**視聴回数の数字は画像に載せない** |
| 10 | ワードクラウドの単位 | **チャンネル別7枚＋全体1枚**。語数が少ないチャンネルは警告バッジを出す |
| 11 | ワードクラウドの語数しきい値 | 文字数ではなく**延べ語数**で判定する（サンプル生成で、文字数は足りても語数が足りない状態が確認されたため） |
| 12 | 形態素解析 | janome（純Python・依存なし）。Streamlit Cloud で確実に動く |
| 13 | チャンネル定義の単一化 | チャンネル名・表示名・テーマの対応はスナップショットの `channels` を唯一の正とする。`CHARACTER_MAPPING` や `CHANNEL_THEMES` に同じ情報を持たせない |
| 14 | アップロードファイルの扱い | Vercel 側（B）は**ブラウザ内だけで処理**しファイルは外に出ない。Streamlit 側（C・D）は**サーバーへ送られて**メモリ上で処理され、保存はしない。この差をアプリごとに正しく表示する |
| 15 | 公開範囲 | SNS投稿前提。自分のコメントなので自己責任で扱う |

## 7. 前提と制約

- **視聴履歴には視聴時間・完了率が入っていない。** あるのは再生開始のイベント列だけなので、「よく見ている」＝履歴への出現回数と定義する。
- **視聴履歴は Google 側の保存期間設定により古い分から削除される。** 実測したエクスポートは 2026-04-01 〜 2026-07-10 の 3.3ヶ月分しか含まなかった。未視聴判定は「履歴に残る範囲で未視聴」であり、この但し書きを画面に常時表示する。
- **Takeout は手動エクスポート。** B・C・D はエクスポート時点のデータを見る。再エクスポート手順への導線を置く。
- **コメント CSV の `Channel ID` は自分のチャンネル ID** であって、コメント先の動画のものではない。チャンネル判定は必ず `Video ID` 経由で行う。
- **Takeout のロケールは環境によって変わる。** 実測データは英語（`"Watched …"`）だった。日本語（`"… を視聴しました"`）と両方を受け付ける。
- **アップロードファイルの扱いはアプリで違う。** B（Vercel）は Web Worker でブラウザ内処理し、ファイルはネットワークに出ない。C・D（Streamlit）は**サーバーへ送られて**メモリ上で処理される（保存はしない）。それぞれの画面に正しく表示する。
